# План кооперативного мода (IP:port, host-authoritative)

Этот документ описывает минимально жизнеспособную архитектуру кооператива для X-Ray Monolith c моделью **host-authoritative** через прямое подключение по **IP:port**.

## 1) Цели MVP

- Целевой онлайн: **до 32 игроков** в сессии (архитектура без жёсткого лимита, но с практическим профилированием под 32).
- Хост является единственным авторитетным источником истины по миру.
- Клиенты отправляют только намерения (input/команды), а не прямые изменения мира.
- Репликация: позиции/анимации, стрельба, урон, базовые события AI.
- Подключение к сессии напрямую: клиент вводит `IP:port` хоста.

## 2) Сетевая модель

### Host-authoritative

- **Хост**:
  - симулирует мир, AI, физику, баллистику и урон;
  - валидирует действия клиентов;
  - рассылает снапшоты состояния и события.
- **Клиент**:
  - выполняет локальный prediction для своего персонажа;
  - интерполирует/экстраполирует удалённые сущности;
  - при получении authoritative state делает reconciliation.

Почему это важно: меньше читов, проще держать детерминизм логики и совместимость со скриптовой экосистемой.

## 3) Транспорт и подключение

Рекомендуемый транспорт: **UDP + собственный протокол над ним** (reliability layer для нужных сообщений).

### Схема подключения

1. Хост поднимает listening socket на заданном порту.
2. Клиент подключается по `IP:port`.
3. Клиент отправляет `Hello` с версией протокола и сессионным `RuntimeClientId`.
4. Хост валидирует совместимость (версия, whitelist контента), назначает `NetPeerId` и отвечает `Welcome`.
5. Клиент получает `baseline snapshot`, догоняет состояние мира и входит в real-time фазу.

### Идентификатор клиента для мультиоконного теста

- При **каждом запуске клиента** генерируется новый `RuntimeClientId` (например, UUIDv4/random 128-bit).
- `RuntimeClientId` не должен быть постоянным между перезапусками.
- Хост использует `NetPeerId` как внутренний сетевой идентификатор соединения, независимо от аккаунтов/платформ.

### Каналы

- **Reliable ordered**: handshake, spawn/despawn, инвентарь, квестовые/скриптовые события, подтверждённые команды.
- **Unreliable sequenced**: частые transform update, look direction, animation state.

## 4) Протокол сообщений (минимум)

- `C2H_Hello`: версия, `RuntimeClientId`, сведения о сборке/мод-паке.
- `H2C_Welcome`: назначенный `NetPeerId`, server tick base, правила сессии.
- `C2H_InputFrame`: input игрока + номер тика + timestamp.
- `H2C_Snapshot`: состояние релевантных сущностей на тик.
- `H2C_Event`: дискретные события (выстрел, hit-confirm, death, script_event).
- `H2C_Spawn/Despawn`.
- `C2H_Ack`: подтверждение последнего снапшота.
- `C2H_ActionRequest`: запрос клиента к хосту на выполнение действия.
- `H2C_ActionResult`: результат запроса (`accepted/rejected/deferred`) + причина.
- `C2H_SyncRequest`: запрос принудительной ресинхронизации сущности/состояния.
- `H2C_SyncState`: authoritative состояние по запросу.
- `Ping/Pong`: измерение RTT/джиттера.

Рекомендация: бинарная сериализация с `version tag` в заголовке пакета.

## 5) Клиентские запросы к хосту (обязательный поток)

Нужен отдельный, формализованный путь для клиентских запросов:

- Клиент не применяет мироизменяющие действия напрямую.
- Вместо этого отправляет `C2H_ActionRequest(action, payload, client_tick)`.
- Хост валидирует запрос (дистанция, состояние, cooldown, права).
- Хост возвращает `H2C_ActionResult` и, при успехе, рассылает событие/снапшот всем клиентам.

Примеры действий через `ActionRequest`:

- интеракция с дверью/контейнером;
- использование предмета;
- скриптовое событие, изменяющее состояние мира.

## 6) Тикрейт и синхронизация

- Серверный тик: 20–30 Hz (начать с 20 Hz для стабильности).
- Снапшоты: 10–20 Hz, delta-compression относительно последнего ack от клиента.
- Клиентский render: интерполяционный буфер 100–150 мс.

База анти-рассинхрона:

- sequence number для каждого пакета;
- server tick id в каждом snapshot/event;
- периодический full snapshot (например, раз в 3–5 сек);
- возможность точечной ресинхронизации через `C2H_SyncRequest`.

## 7) Что синхронизировать в первую очередь

1. Игроки: transform, stance, active item, fire/reload state, hp/stamina.
2. NPC рядом с игроками: transform + combat state (упрощённо).
3. Важные интерактивы: двери, контейнеры, loot ownership.
4. Критичные скриптовые флаги (сюжет/квест).

Не синхронизировать на MVP всё подряд — только релевантный радиус + важные сущности.

## 8) Скрипты и authoritative-границы

- Любая скриптовая логика, влияющая на мир (спавн, урон, квест-флаги), должна инициироваться или подтверждаться хостом.
- На клиенте разрешать только визуальные эффекты и предсказание локального input.
- Ввести `net_script_event(name, payload, authority)`:
  - `authority = host_only` (по умолчанию);
  - `authority = client_request` (клиент запрашивает, хост валидирует через `ActionRequest`).

## 9) Безопасность и валидация

- Rate limit на клиентские RPC/inputs/request-ы.
- Валидация:
  - скоростей перемещения;
  - допустимых transition состояний оружия;
  - дистанций интеракций;
  - частоты запросов `ActionRequest/SyncRequest`.
- Версионирование контента: hash списка обязательных файлов/аддонов в handshake.

## 10) Масштабирование до 32 игроков

- Interest management (AOI): отправлять клиенту только релевантные сущности в радиусе/секторе.
- Приоритизация апдейтов: игроки и бой — highest priority, дальние NPC — пониженную частоту.
- Бюджеты сети: ограничение snapshot size/сек и деградация частот для низкого приоритета.
- Пул объектов и батч-сериализация для снижения аллокаций.

## 11) Пошаговый roadmap

### Этап 1 — Сетевой каркас

- Listening socket по порту и подключение по IP:port.
- Handshake (`Hello/Welcome`) + назначение `NetPeerId`.
- Ping/pong, логирование и базовые disconnect/reconnect сценарии.

### Этап 2 — Игроки

- Репликация только игроков.
- Client prediction + reconciliation для локального игрока.
- Spawn/join/leave flow и проверка мультиоконного запуска с разными `RuntimeClientId`.

### Этап 3 — Бой

- Выстрел и урон только на хосте.
- Репликация hit/death событий.

### Этап 4 — NPC + интерактивы

- Базовая синхронизация боевых NPC рядом с игроками.
- Двери/контейнеры/лут с authoritative lock.
- `ActionRequest/ActionResult` для интерактивов.

### Этап 5 — Скриптовый слой

- API для net-событий в Lua.
- Белый список сетевых script events.
- Хост-валидация клиентских script-запросов.

## 12) Минимальный техдолг, который стоит заложить сразу

- Replayable net-log (входящие/исходящие пакеты с тиком).
- Детерминированный идентификатор сущности `NetEntityId`.
- Метрики в overlay: RTT, packet loss, server tick drift, snapshot size, queued requests.

## 13) Практические советы по внедрению в этот движок

- Не пытайтесь сразу «сетевизировать всё» — выберите один уровень/режим песочницы.
- Оставьте одиночную игру как отдельный кодпуть (или режим loopback-host), чтобы не ломать существующие моды.
- Начните с C++ транспорта и репликации, а Lua подключайте после стабилизации базовых сущностей.
- Все спорные решения логируйте в единый net-channel лог для последующего профилирования.
