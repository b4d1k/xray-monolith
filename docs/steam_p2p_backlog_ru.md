# Технический backlog кооператива (IP:port, host-authoritative)

Документ — продолжение архитектурного плана и перевод его в исполнимые задачи по подсистемам движка.

## 0) Принципы внедрения

- Сначала вертикальный срез: `подключение -> 2 игрока -> перемещение -> снапшоты`.
- Все изменения делаем с флагом режима `coop_enabled`, чтобы не ломать одиночный режим.
- Для каждой задачи обязателен лог в net-channel и измеримый критерий готовности.

## 1) Эпик A — Сетевой фундамент (ядро транспорта)

### A1. Transport bootstrap (UDP listener/client)

**Подсистемы:** `xrNetServer`, сетевой слой в `xrGame`.

**Задачи:**
- [ ] Поднять UDP listener на хосте с конфигурируемым портом.
- [ ] Реализовать клиентское подключение по `IP:port`.
- [ ] Ввести lifecycle состояний соединения: `Disconnected -> Connecting -> Handshake -> Active -> Timeout`.
- [ ] Добавить heartbeat (`Ping/Pong`) и timeout disconnect.

**DoD:**
- Хост и клиент устанавливают соединение локально и по LAN.
- В логах фиксируются state-transition, RTT и причина disconnect.

**Риски:**
- NAT/фаерволы могут блокировать UDP.
- Плавающие таймауты на слабых сетях.

### A2. Handshake и идентификаторы

**Задачи:**
- [ ] Реализовать `C2H_Hello` и `H2C_Welcome`.
- [ ] Генерировать `RuntimeClientId` на каждом запуске клиента (не сохранять между сессиями).
- [ ] Назначать серверный `NetPeerId` после успешной валидации.
- [ ] Добавить проверку версии протокола и hash контента.

**DoD:**
- Мультиоконный запуск одного билда даёт разные `RuntimeClientId`.
- Несовместимая версия протокола корректно отклоняется с причиной.

**Риски:**
- Конфликты формата hash при разных сборках модов.

### A3. Базовый слой надёжности

**Задачи:**
- [ ] Заголовок пакета: `msg_type`, `seq`, `ack`, `ack_bits`, `server_tick`, `channel`.
- [ ] Реализовать reliable-очередь для критичных сообщений.
- [ ] Реализовать unreliable-sequenced для трансформов.
- [ ] Ограничить resend-rate и размер очередей.

**DoD:**
- Потеря 5–10% пакетов не ломает handshake и критичные действия.
- Устаревшие unreliable-пакеты отбрасываются корректно.

## 2) Эпик B — Репликация игроков

### B1. Spawn/join/leave

**Подсистемы:** `xrGame`, `xrServerEntities`.

**Задачи:**
- [ ] Добавить сетевое создание/удаление player entity.
- [ ] Привязать `NetPeerId` к игроку на хосте.
- [ ] Реализовать корректный leave/timeout cleanup.

**DoD:**
- 2–8 клиентов стабильно входят/выходят без утечек сущностей.

### B2. Input -> authoritative simulation

**Задачи:**
- [ ] Реализовать `C2H_InputFrame` с нумерацией тиков.
- [ ] Хост симулирует движение на основе input, а не клиентских координат.
- [ ] Клиент получает authoritative transform в `H2C_Snapshot`.

**DoD:**
- Невозможно "телепортироваться" отправкой фальшивых координат.

### B3. Prediction/Reconciliation

**Задачи:**
- [ ] Локальный prediction для своего игрока.
- [ ] Reconciliation по `server_tick`.
- [ ] Интерполяция удалённых игроков с буфером 100–150мс.

**DoD:**
- При RTT до ~120мс управление остаётся отзывчивым, без сильных рывков.

## 3) Эпик C — Снапшоты и interest management

### C1. Snapshot pipeline

**Подсистемы:** `xrGame`, `xrNetServer`.

**Задачи:**
- [ ] Реализовать `H2C_Snapshot` с baseline/delta.
- [ ] Добавить периодический full snapshot (каждые 3–5 сек).
- [ ] Ввести per-client ack state.

**DoD:**
- Клиент корректно восстанавливается после потери нескольких delta-пакетов.

### C2. AOI (area of interest)

**Задачи:**
- [ ] Ввести фильтрацию сущностей по радиусу/сектору.
- [ ] Ввести уровни приоритета обновлений (игроки/бой/NPC/мир).
- [ ] Ограничить бюджет snapshot bytes/sec на клиента.

**DoD:**
- На 16+ клиентах нет взрывного роста трафика на неактивных участках карты.

## 4) Эпик D — Бой и интерактивы

### D1. Authoritative combat

**Задачи:**
- [ ] Любой выстрел/урон считается только на хосте.
- [ ] Клиент отправляет намерение выстрела, хост подтверждает событием.
- [ ] Добавить `H2C_Event` для hit/death.

**DoD:**
- Локальная модификация клиента не даёт некорректный урон.

### D2. ActionRequest/ActionResult

**Задачи:**
- [ ] Реализовать `C2H_ActionRequest` для дверей/контейнеров/юза предметов.
- [ ] Реализовать `H2C_ActionResult` с кодами причин отказа.
- [ ] Добавить rate-limit и anti-spam политику.

**DoD:**
- Клиент не может напрямую менять состояние интерактивов без одобрения хоста.

### D3. SyncRequest

**Задачи:**
- [ ] Реализовать `C2H_SyncRequest` для точечной ресинхронизации.
- [ ] Реализовать `H2C_SyncState` для выбранной сущности/подсостояния.

**DoD:**
- Десинхрон отдельной сущности устраняется без полного reconnect.

## 5) Эпик E — Lua/скриптовая сеть

### E1. Lua API для сетевых событий

**Подсистемы:** Lua биндинги, скриптовый рантайм.

**Задачи:**
- [ ] Ввести `net_script_event(name, payload, authority)`.
- [ ] Разделить режимы `host_only` и `client_request`.
- [ ] Ввести белый список допустимых client-request событий.

**DoD:**
- Скрипт-клиент не может вызвать неразрешённое мироизменяющее событие.

### E2. Валидация и наблюдаемость

**Задачи:**
- [ ] Логировать все script-request с вердиктом.
- [ ] Добавить debug-команду просмотра очереди запросов.

**DoD:**
- Причина отказа каждого script-request видна в логах.

## 6) Эпик F — Инструменты, тесты, метрики

### F1. Net-log и диагностика

**Задачи:**
- [ ] Replayable net-log входящих/исходящих сообщений.
- [ ] Overlay метрики: RTT, jitter, packet loss, snapshot size, queue depth.

**DoD:**
- По логу можно воспроизвести и локализовать десинхрон.

### F2. Тест-матрица

**Задачи:**
- [ ] Сценарии: 2/8/16/32 клиента, reconnect, packet loss, high RTT.
- [ ] Тест мультиоконного запуска с уникальными `RuntimeClientId`.
- [ ] Smoke-набор регрессии одиночного режима при `coop_enabled = false`.

**DoD:**
- Есть repeatable чеклист, покрывающий критичные сетевые потоки.

## 7) Порядок реализации (рекомендуемый)

2. B1 -> B2 -> B3
3. C1 -> C2
4. D1 -> D2 -> D3

6. F1 -> F2 (параллельно со всеми этапами)

## 8) Минимальные релизы

### R1 (технический прототип)
- Подключение по IP:port.
- 2–4 клиента, только игроки и перемещение.

### R2 (играбельный core)
- До 8–16 клиентов.
- Бой + базовые интерактивы через `ActionRequest`.

### R3 (масштабирование)
- Цель до 32 клиентов.
- AOI, сетевые бюджеты, стабилизация и профилирование.
